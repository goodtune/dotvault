# Daemon lifecycle

> Carved from CLAUDE.md. Startup ordering, the config-refresh loop, and reload semantics.

## Daemon Lifecycle

1. Load config (file or registry)
2. Create Vault client, attempt token reuse (DOTVAULT_TOKEN env or `~/.dotvault-token`)
3. Start web UI if enabled (before auth, so it can serve browser-based login)
4. Authenticate if needed: web mode routes all auth through the browser login view at `/`; CLI mode uses method-specific flows (OIDC browser, LDAP terminal prompt, token file). A non-interactive host with neither a web UI nor a TTY does not give up — it registers a synchronous token-file watch and idles until an external facility (e.g. a login profile running `dotvault login`) writes a usable token, then resumes startup. The watch is registered before the no-token decision so a token written during startup cannot be missed; this replaced the previous behaviour where a headless daemon idled until shutdown and required a restart to pick up a token (`waitForHeadlessToken`, `cmd/dotvault/main.go`).
5. Start token lifecycle manager (renews at 75% TTL, exponential backoff 1s-5m on failure)
6. Start RefreshManager (rotates expiring credentials for `Refresher` engines, e.g. JFrog) and WatchManager (re-mirrors upstream sources for `Watcher` engines, e.g. Copy)
7. Run enrolment check (wizard if any credentials missing in Vault)
8. Start sync engine: initial sync, then hybrid event+poll loop
9. Background config-refresh loop (all daemon modes — web, headless, CLI) re-runs the startup loader every `remote_config.refresh_interval` (default: sync interval): the remote overlay re-fetches with an ETag-conditional GET, and dynamic-section changes fan out — enrolments to the enrolment manager (CLI mode), RefreshManager, WatchManager, and the web enrolment runner (deferred while an enrolment is mid-run); rules and sync interval to `sync.Engine.UpdateConfig` (state entries for removed rules pruned, ticker reset, immediate sync trigger) and the web server's locked snapshots. The loop also runs a pass immediately on a manual reload request (SIGHUP, or the tray's "Reload config" entry on Windows) instead of waiting for the next tick, and warns — naming the sections — when a reload finds static sections changed, since those need a restart.
10. Mount the filesystem if `fuse.enabled` (`startFUSE`, `cmd/dotvault/fusemount.go`), after the first successful auth for the same reason the SSH agent listener waits: every read it serves is a Vault call, so a mount that came up first would answer errors to anything that looked at the directory — including whatever indexes a desktop user's home. Never fatal, and deliberately not retried.
11. On Windows, install a system-tray icon (`internal/tray/`) with "Reload config", Exit, and (when web is enabled) "View web UI" entries; the tray owns the main goroutine because the Win32 message pump must run on a locked OS thread, while the sync loop moves to a goroutine. On non-Windows the same call simply blocks on ctx.

The daemon watches `~/.dotvault-token` for replacement and re-reads it immediately via `LifecycleManager.Reload` — handy for picking up a token freshly written by `dotvault login` without waiting for the 5-minute lifecycle tick. On Linux this uses inotify on the token file's parent directory (`internal/tokenwatch/`, watching the directory rather than the inode because atomic writers replace it via temp-file+rename); creation and write-completion events trigger a reload, deletes are ignored so the daemon keeps using its current in-memory token until a new one is written. On non-Linux platforms the watcher is a no-op. This replaces the previously shipped `dotvault-token-watch.path`/`.service` systemd units, which forwarded token-file changes to the daemon via SIGHUP out-of-process. SIGHUP remains the daemon's manual reload trigger on every platform where it is delivered (not Windows): it re-reads the token file (`LifecycleManager.Reload`) **and** nudges the config-refresh loop to re-run the loader immediately. The packaged systemd unit wires it as `ExecReload=`, so `systemctl --user reload dotvault.service` is the canonical gesture; that (like `systemctl --user kill --signal=SIGHUP dotvault.service`) targets the unit's MainPID rather than scanning the process table for anything named `dotvault`, so a developer running `go run ./cmd/dotvault` or `dotvault sync` from a shell while the daemon also happens to be running won't have those side processes SIGHUP'd (their default disposition for SIGHUP is *terminate*).

Config reload via SIGHUP is **dynamic sections only**. The dynamic sections — rules, enrolments, and the sync interval — apply in place, exactly as they do on the config-refresh tick they already converge on in every daemon mode (whether the change came from the remote overlay or an edited local config); the signal just skips the wait. `fuse` is refused outright in a remote document (`partialStaticSections`), like every other static section — a remote service must not be able to mount a filesystem on the machine. `remote_config` is dynamic too: the withRemote loader rebuilds the overlay fetcher when the section changes and the loop re-derives its tick cadence (explicit `remote_config.refresh_interval`, else the sync interval) after every pass — though a *remote* document still cannot carry the section, which stays local-only. The static sections (vault, web, api, agent, fuse, observability, and the top-level `bypass_system_config` flag) configure subsystems constructed once at startup and still require a full restart — a reload that finds them changed logs a WARN naming the changed sections rather than half-applying them (`staticSections`/`changedStaticSections`, `cmd/dotvault/main.go`; the comparison reduces `observability.headers` to a SHA-256 digest so the snapshot doesn't re-retain the scrubbed bearer tokens). The deliberate non-choice: exiting with a magic code for systemd to restart would only work under a supervisor — a manually-run daemon, macOS launchd without `KeepAlive`, or dotvaultw would simply die — and would discard in-memory-only state (borrowed peer tokens, web sessions). On Windows, where SIGHUP is never delivered, the tray's "Reload config" entry drives the same token re-read + immediate refresh pass for both `dotvault.exe run` and `dotvaultw.exe`. Known cadence limitations: the WatchManager poll interval and the RefreshManager check interval are fixed at construction.
