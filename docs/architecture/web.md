# Web UI internals

> Carved from CLAUDE.md. The three browser surfaces (login `/`, first-run wizard `/setup/`, main site `/ui/`), the request surface, and the security posture of each endpoint. User-facing: `docs/web-ui.md`.

## Web UI

Server-rendered Go templates embedded via `embed.FS`, with no build step and no client-side application. Disabled by default (`web.enabled: true` to enable). Loopback-only binding is a hard invariant — the daemon refuses to start if `web.listen` resolves to a non-loopback address. There were two surfaces until the Preact SPA was removed; the pages below are now the whole UI.

The browser sees three surfaces, and which one it lands on is decided entirely by `GET /` (`handleRoot`, `internal/web/ui_login.go`):

1. **The login view at `/`** when the daemon holds no token (`internal/web/ui_login.go`, chrome-less).
2. **The first-run enrolment wizard at `/setup/`** when authenticated with *nothing* enrolled yet (`internal/web/ui_setup.go`, chrome-less).
3. **The main site under `/ui/`** otherwise.

### Login view (`/`)

Dispatches on `auth.BaseMethod(vault.auth_method)`: an OIDC button (`/auth/oidc/start`), an LDAP credential form, a token paste form, or — for the three certificate variants, which need no credential — a waiting card. The one interactive moment certificate auth has is the one-time bootstrap: while a `BootstrapLogin` is waiting, the card becomes whichever credential form `vault.mtls.bootstrap_method` names, framed by `bootstrapNoticeHTML` as an enrolment rather than a sign-in, and afterwards (`/?issuing=1`) reports that the certificate is being issued.

**The login view loads no JavaScript at all.** Its waiting states — an MFA push awaiting approval, a certificate being issued — advance with `<meta http-equiv="refresh">`, so a login works with scripting disabled and the strict CSP applies unchanged (`uiScriptedPath` deliberately excludes it). The one state that must *not* auto-refresh is the TOTP prompt: a reload would wipe the passcode being typed, so that card carries no refresh and the form submit drives it instead.

LDAP's async `LoginTracker` session id rides a `dotvault_login` cookie (HttpOnly, `Path=/login`) rather than the URL — it is a bearer secret for that in-flight login, and a URL would put it in history and any Referer. It is not an authentication cookie: the daemon's session is its Vault token, held server-side, and the cookie is cleared the moment the login reaches a terminal state.

Token adoption for *every* browser login funnels through one helper, `consumeLoginToken` — bootstrap divert first (raw token to the waiting `BootstrapLogin`, adopting nothing), then `Downscope` → `SetToken` → `WriteTokenFile` → `authDone`. Adding a login flow means calling that helper, not re-deriving the ordering.

### First-run enrolment wizard (`/setup/`)

Shown **only while no enrolment has been completed** (`EnrolmentRunner.NeedsWizard`), which is the deliberate difference from the enrolment page it replaces: that one reappeared whenever *any* enrolment was outstanding, so it kept interrupting users who had knowingly skipped one. Once anything is enrolled — or every enrolment has been addressed, completed or skipped alike — or the user leaves it with work outstanding, the main site takes over and individual enrolments are managed from `/ui/enrolments/`.

Two consequences worth keeping straight:

- A skipped enrolment counts as *addressed*: the user was shown it and declined, so it does not keep the wizard standing. `Complete()` still latches (`dismissed`) for the other way out — leaving with enrolments genuinely outstanding. A config reload builds a new runner and so re-evaluates from scratch, which is intended.
- **Unattended enrolments are excluded from the wizard entirely** (`enrol.EngineUnattended`, today only the Copy engine) — from the decision to show it *and* from the page itself (`wizardStates`). They are evidence in neither direction, and the direction that bit was completion: a copy enrolment finishes on its own, often before the user has seen anything, so counting it satisfied `NeedsWizard`'s "something is already enrolled" test and a fresh user with a copy enrolment configured never saw setup at all. They are then also not *rendered*, since the wizard's purpose is the work a user must do and a card they cannot act on is noise; they remain fully available under `/ui/enrolments/`. Every consumer of the wizard's contents must narrow through `wizardStates`, `allAddressed` included — computing the footer over the unfiltered list would let a pending copy enrolment hold the exit control on "Skip remaining" permanently, offering to skip something the page does not show.
- `EnrolmentRunner.Wait()` — what blocks daemon startup — returns immediately unless `NeedsWizard()`. Gating it on "anything pending" instead would hang the sync engine on a host that has credentials and one outstanding enrolment, since the user is sent straight to the site and nothing would ever call `Complete()`. `handleRoot` also calls `Complete()` whenever it decides the wizard is not needed, so reaching the main site always releases that wait.

The wizard's exit control (`setup-footer`) is re-patched alongside the card, from the shared `allAddressed` predicate. It was previously rendered once with the page as a submit button carrying `{{if .AnyRunning}}disabled{{end}}` while only the *card* was patched, so finishing the last enrolment left a user parked on a completed wizard whose only control still read "Skip remaining" and was still disabled. Nothing in it is disabled now — leaving mid-run is harmless, and a disabled control is precisely what went stale.

Its two states are **different elements, deliberately**. With everything addressed there is nothing to decide, so it is a plain `<a href="/">` and the server re-derives on that GET where the user belongs. With enrolments still outstanding, leaving *means* abandoning them, so it stays a `POST /setup/complete`: a link to `/` in that state would be answered by `handleRoot` with a redirect straight back to the wizard, making a control labelled "Skip remaining" a no-op loop — the trap three reviewers independently found when the whole footer was made a link. Relatedly, "skipped" now counts as addressed, so skipping everything stands the wizard down on its own rather than needing the explicit dismissal.

The wizard renders the same `enrol-card` fragment the main site does, with `ActionBase` selecting where the card's forms post (`/setup` vs `/ui/enrol`) and the fragment poll URL carrying that base so a patched card keeps its own actions. Cards get a per-key `ElementID` (hex of the key) because the wizard renders many at once and a shared id would send every patch to the first card. A card waiting on `io.PromptSecret` **stops polling** — a patch replaces the whole card, so a 2s refresh would wipe the half-typed passphrase and detach the field mid-click.

### Main site (`/ui/`)

Every page is Go `html/template` (`internal/web/uitmpl/*.tmpl`, embedded) with real URLs; interactivity comes from [datastar](https://data-star.dev) (`internal/web/uiassets/datastar.js`, vendored + embedded; Go side uses `github.com/starfederation/datastar-go`) patching server-rendered fragments over SSE. The stylesheet (`/ui/assets/style.css`) is the one the removed SPA used, so its look and feel carried over unchanged; layout differs by design — a left accordion nav (Enrolments / Remotes / Secrets, one section expanded per route) rather than header buttons, and the config page keeps the nav instead of a "back to dashboard" button.

Pages: `/ui/` (dashboard: header status bar + `secret_view_text` markdown), `/ui/secrets/` (+ `/ui/secrets/<key>` detail with reveal/copy, `/ui/secrets/<folder>/` listing; trailing-slash spellings accepted), `/ui/enrolments/` (+ `/ui/enrolments/<engine>/<key>/` where the enrolment runs — the card states parse engine output in `ui_enrol.go`, and a running card polls its own fragment every 2s), `/ui/remotes/` (+ `/ui/remotes/<host>/` edit form, which also shows the pinned host key — SHA256 fingerprint plus a reveal control for the full authorized-key line, or a CA-trust note when nothing is pinned; add/save/delete are plain form POSTs through the same `sshfwd.Registry`, including the 409-fingerprint confirm gesture; both pages subscribe to `/ui/sse/ssh`, a change-diffed SSE stream that live-patches the nav dots plus the page's own region (the table on the index, the state line on the detail page), so state changes from any writer — the page itself, another tab, the CLI via the daemon's API, or the reconnect loop — appear without a refresh), `/ui/config/` (same `buildConfigViewModel` the JSON `/api/v1/config` serves — one builder, two surfaces).

Conventions that must hold when extending it:

- **Request posture.** Page GETs redirect unauthenticated browsers to `/`, which owns every login flow. Fragment GETs 401. All browser POSTs — `/ui/`, `/setup/` and the login forms alike — require a **present, same-origin `Origin` header** (`requireSameOrigin`, wrapped by `requireUIWrite` where authentication is also needed). That is the CSRF control for this surface: browsers attach Origin to every POST, while server-rendered forms and multi-tab use make an issue-then-spend token store a poor fit. Unlike the peer-action endpoints, an absent Origin is rejected — these endpoints have no curl consumer. The login POSTs need it as much as the authenticated ones: without it a hostile page could post its own Vault token to `/login/token` and have the daemon adopt an attacker-chosen identity.
- **Secrets never ride in page HTML.** The detail table renders masked cells; the eye button `@get`s a reveal fragment (which re-masks itself after 30s via `data-init__delay.30s`), and the clipboard button copies **server-side** via the shared `guardedLaunch` + `clipboard.Set` path — the value never reaches the browser. The "copy token" header button works the same way.
- **CSP.** Datastar-serving responses (`uiScriptedPath`: `/ui/` and `/setup/`) get `script-src 'self' 'unsafe-eval'` (datastar compiles attribute expressions with the Function constructor) and `style-src 'self' 'unsafe-inline'` (the `style="display: none"` anti-flicker idiom on `data-show` elements); every response carries `frame-ancestors 'none'`. Keep `uiScriptedPath` in step when adding a scripted page — a page missed there renders fine and then silently refuses to evaluate any datastar expression, which is how the wizard's card poll was first found broken — the Origin CSRF check cannot see framing, so clickjacking of gestures like "Trust and add" is closed off here. Inline *scripts* stay forbidden on both surfaces; do not use datastar's `ExecuteScript`/`Redirect` SSE helpers, which inject inline `<script>` tags the CSP blocks — use HTTP 303 redirects from form POSTs instead.
- **Metrics.** `/ui/`, `/setup/` and `/login/` paths collapse to one route label each (`/ui/*` in particular embeds secret keys and hostnames).
- html/template treats `data-on:*` attributes as JavaScript context and escapes interpolated URLs as JS strings (`\/`, `&`) — correct, since datastar evaluates them as JS; don't "fix" the escaping. But `data-init*` and other non-`on` datastar attributes get plain HTML-attribute escaping even though datastar evaluates them as JS too, so the only safe interpolation in ANY datastar attribute is a strictly URL-encoded value (`url.Values.Encode` output) — pinned by `TestUIFragmentURLsAreQueryEncoded`.
- The vendored browser bundle's provenance and re-vendor procedure live on the `uiAssetsFS` embed comment in `internal/web/ui.go`; the Go SDK versions independently and is dependabot-covered via `gomod`.

The same server can additionally (or instead) serve its API over a per-user Unix socket when `api.enabled` — see "Local API socket" under Authentication for the route split, the Origin consequence, and why the two surfaces are enabled independently.

### Routes

(The page routes are described in the subsections above; this list is the request surface.)

**Browser surface (registered only when `web.enabled`; all POSTs are Origin-checked):**
- `GET /` — login view, or a redirect onward to `/setup/` or `/ui/`
- `GET /auth/oidc/start`, `GET /auth/oidc/callback` — the OIDC round trip. **These two paths are a compatibility surface**: the callback URI is registered in Vault's `allowed_redirect_uris` and in the identity provider, so it is not free to rename
- `POST /login/ldap` — start an async LDAP login, then redirect to the progress page
- `GET /login/ldap` — LDAP progress page (MFA wait or TOTP prompt); adopts the token once Vault authenticates
- `POST /login/ldap/totp` — submit an MFA passcode
- `POST /login/token` — validate and adopt a pasted token (403 under certificate auth)
- `GET /setup/`, `POST /setup/{start,skip,reset,secret}` — the first-run wizard and its enrolment actions (leaving the wizard is a plain link to `/`, not a POST)
- `GET /favicon.ico` — the embedded icon (browsers request it unprompted)

**Health probes** (served on every enabled HTTP surface — the loopback web listener and/or the local API socket; a daemon with neither has nothing to probe):
- `GET /healthz` — liveness, always 200 while serving
- `GET /readyz` — readiness, 200 once the daemon holds a Vault token AND has marked the initial sync complete (mirrors the `sd_notify(READY=1)` contract). 503 otherwise. Token check reflects the cached in-memory state, not a per-probe Vault round-trip.

**API:**
- `GET /api/v1/csrf` — issue CSRF token (one-time use, max 1000 in memory)
- `GET /api/v1/status` — server status (auth, vault version, token TTL, sync state, vault address, kv_mount, user_prefix, username). Also carries `bootstrap: {active, method}` **unauthenticated**, alongside `auth_method`: a client needs it to choose a login form *before* any token exists, which is the whole point of a bootstrap. `active` is true only while a `BootstrapLogin` is waiting; the token itself is never exposed here or anywhere else. Note `auth_method` is the *base* method (`auth.BaseMethod` strips `+tpm`/`+os`), so all three cert variants arrive as `mtls` and the login view dispatches on that single string
  Also carries a `fuse` block (mountpoint, access mode, mount state, last error) when a filesystem is configured, wired in post-construction via `SetFUSEStatus` because the mount is built after the first successful auth. Unauthenticated like the sibling blocks: it reports where the filesystem is and whether it came up, never anything from inside it
- `GET /api/v1/rules` — configured sync rules
- `GET /api/v1/config` — redacted view of the running config for the UI
- `GET /api/v1/config/download?format=yaml|reg` — full config download for the Effective Configuration screen
- `GET /api/v1/secrets/{path}` — list or reveal secret (reveal requires `?reveal=true`)
- `POST /api/v1/sync` — trigger immediate sync (CSRF-protected)
- `POST /api/v1/remote/browse` — open a form-posted `url` (body only; query string ignored) in this host's default browser (`internal/web/browse.go`). The outbound counterpart of `GET /api/v1/token` over the same forwarded socket: a headless peer (or `dotvault browse`) hands a URL back to the workstation so browser-driven flows open where a browser exists. **Deliberately NOT CSRF-protected** — the consumer is a bare curl/form POST over a forwarded Unix socket with no practical way to run the issue-then-spend CSRF handshake, and the handler reads no state and returns nothing sensitive. Cross-site browser traffic (which the loopback Host check alone would pass, since a cross-origin form POST is a CORS "simple request") is rejected by an **Origin check** instead: a present `Origin` header must name the daemon's own origin — a loopback hostname (`originAllowed` → `loopbackHostname`, the same allowlist as the Host check) **on the daemon's own listener port** (bound `listenAddr` preferred, `cfg.Listen` pre-Start), because an Origin names whichever server served the page and a hostname-only check would admit pages from any other loopback-served origin; curl and the CLI send none and pass, hostile pages always send theirs (or `null`) and are 403'd. The other load-bearing control is the strict allowlist (`ValidateBrowseURL`: http/https with a host, no embedded `user:pass@` credentials), which keeps `file://` and custom-protocol strings away from xdg-open/ShellExecute. The opener runs under a bounded wait (`browseOpenTimeout`, 8s < the CLI's 10s POST timeout) so a hung launcher can't strand the handler, and behind a single-flight gate (`browseOpenMu.TryLock`, concurrent requests get 503) because an abandoned hung launcher can't be killed and unbounded requests would pile up stuck goroutines. Log lines carry scheme+hostname only, at every level — query strings and even path segments can be capability-bearing, and the requester already knows the URL it posted. Browser launch is injected via `ServerConfig.OpenBrowser` (defaults to `browser.OpenURL`; tests fake it); the middleware's loopback Host check applies as on every route.
- `POST /api/v1/remote/notify` — raise a native desktop notification from a form-posted `level`/`title`/`body`/`action_url` (`internal/web/notify.go`). Optional `action_url` (http/https, same allowlist as browse) makes the notification open the URL on click (Windows) or appends it to the body (macOS/Linux). The sibling of `remote/browse` with the identical no-CSRF / Origin-check / bounded-single-flight posture (both share `guardedLaunch` in `internal/web/launcher.go`). Input validation is `notify.NewMessage` (known level set; title/body sanitized — control chars stripped and Windows-toast-backend metacharacters neutralized: the XML CDATA terminator and the PowerShell here-string `$`/backtick that the fallback would otherwise evaluate as a subexpression → RCE; macOS `%q` and Linux D-Bus argv need no such handling). Delivery is injected via `ServerConfig.SendNotification` (defaults to `notify.Send`; tests fake it). Log lines carry the level and title/body *lengths* only — never the text, which is arbitrary user content that may name secret paths (the same never-log-content posture browse applies to URLs).
- `POST /api/v1/remote/clipboard` — put a form-posted `text` value on this host's clipboard (`internal/web/clipboard.go`). The third peer action, same no-CSRF / Origin-check / bounded-single-flight posture as browse and notify. Input validation is `clipboard.ValidateText` — deliberately a validator, not a sanitizer: clipboard content is data, never interpolated into an evaluated context, and the typical payload is a credential that must arrive byte-for-byte intact, so only content no clipboard can carry (interior NUL, invalid UTF-8) or that signals a caller bug (empty, >64 KiB) is rejected and the text is otherwise written verbatim. The payload is the most secret-bearing of the three peer actions, so the never-log-content posture is strict: log lines carry the text's *length* only, and writer errors are scrubbed of the exact text before logging *and* before being returned in the 502 body (unlike browse, which returns its opener error unredacted) — a best-effort exact-substring scrub layered on writers that never embed their input in errors, not the primary control. Delivery is injected via `ServerConfig.SetClipboard` (defaults to `clipboard.Set`; tests fake it).
- `GET /api/v1/ssh/remotes` / `POST /api/v1/ssh/remotes` / `PATCH /api/v1/ssh/remotes/{host}` / `DELETE /api/v1/ssh/remotes/{host}` — CRUD over the daemon's managed SSH forwards (`internal/web/ssh.go`; see "Managed SSH forwards" below). Unlike the three peer-action routes above, these are **ordinary CSRF-protected mutations**: the Origin-check exemption those use exists because a bare curl over a forwarded socket can't run the issue-then-spend CSRF handshake, and both consumers here (the browser and `dotvault ssh`) can. `POST` performs a live verifying SSH login before persisting; an unpinned host key returns `409` with `{host, fingerprint}`, and the caller must re-`POST` echoing `accept_fingerprint` to commit — the same confirmation gesture the CLI's `--accept-host-key` prompt uses, so a browser session can't degrade the trust decision into blind trust-on-first-use. `PATCH`/`DELETE` validate the unescaped `{host}` path parameter with `sshfwd.ValidateHost` before it reaches the registry (the mux hands wildcards unescaped, so `foo%2Fbar`/`foo%00bar` would otherwise arrive as raw `/`/NUL bytes). All four are thin handlers over `sshfwd.Registry`, so validation, the trust gesture, and the write path are shared with the CLI by construction. `GET /api/v1/status` additionally carries an `ssh` block (per-remote state, reconnect count, last error) fed by the same registry's live status query.

**Security headers:** `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`. The datastar-serving pages get the relaxed CSP variant described under "Main site" above.

**DNS-rebinding defence:** the middleware rejects any request whose `Host` header is not a loopback alias (`127.0.0.1`, `::1`, `localhost`) or the configured `web.listen` hostname. Loopback binding alone doesn't stop a hostile origin from resolving its own DNS name to `127.0.0.1` and using a victim's browser as a relay; the Host check ensures the daemon refuses such requests before any handler runs.

Configurable markdown content via `web.login_text` and `web.secret_view_text` fields rendered by `internal/web/markdown.go`.
