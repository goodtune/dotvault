# Filesystem (FUSE) and the per-user overlay

> Carved from CLAUDE.md. The vaultfs core, the FUSE binding, and the per-user config overlay that merges over policy. User-facing: `docs/guide/filesystem.md`.

## Per-user config overlay

`internal/config/user.go` reads an optional per-user preference file at `paths.UserConfigPath()` (`config.yaml` in `UserConfigDir`, a sibling of the `env` file and `ssh.yaml`) and merges it over the system configuration. It is wired as `withUserOverlay` (`cmd/dotvault/useroverlay.go`) wrapping *outside* `withRemote`, so the composed loader is base → remote → user: the system config and any remote document together are policy, and the user's file expresses preference against that policy, so it must be applied last or a remote refresh could quietly undo the user's choice on the next tick. (A remote document cannot carry `fuse` at all, so today that ordering is belt-and-braces.) `login`/`login-check` (local-only, latency budget) and `reg-import`/`reg-export` (pure converters) deliberately skip it.

**Only `fuse` is user-overridable** (`userOverridableSections`). Any other *known* section is a hard error naming it — silently dropping a `vault:` block would let a user believe they had re-pointed their daemon — while an unknown section warns and is ignored, matching `ParsePartial`'s forward-compatibility posture; a mis-cased known section is a hard error for the same reason it is there (the typed decode would drop it silently).

**Every field ratchets rather than assigning**, and the two booleans deliberately ratchet in *opposite* directions. `enabled` is OR (the user may turn the filesystem on when policy leaves it off, never off when policy enables it); `read_write` is AND (the user may turn writes off, never on). That asymmetry is the point: enabling a read-only mount grants nothing the user's own Vault token could not already do, so an admin's "off" is merely a default — whereas read-write puts every process running as that user one stray `>` away from replacing a credential, so the admin's "no" is binding while the user stays free to be *more* careful than policy requires. `mountpoint` and `cache_ttl` carry no policy weight and the user's value simply wins. The overlay's booleans are `*bool` precisely because the merge must distinguish "no preference" from "explicitly false" — a plain bool would make every user who never mentioned the section look like they were asking to turn it off. An overruled preference logs a WARN naming the field, so a mount the user asked not to have is never silently present.

**The `enabled` ratchet expresses intent rather than enforcing anything.** `mountpoint` is unratcheted, so a user who wants no mount can point it at an unmountable path and get one (a failed mount is logged, non-fatal and unretried). Closing that would mean ratcheting the mountpoint too, which defeats the field's purpose — and would still not help, since a user can `fusermount3 -u` their own mount and the daemon runs as them. What the ratchet buys is that opting out is not a silent, supported config gesture; it is not a control an administrator can lean on.

**The file is refused, not warned about, when it or its parent directory is group/world-writable** (`LoadUserConfig`), and an unreadable permission check is itself an error rather than a licence to proceed. dotvault already refuses a `--config` override against a tamperable system config for weaker stakes, and this file turns a secrets mount on and chooses where the secrets land; the directory is checked as well as the node because a writable parent lets the file be swapped wholesale, the same reasoning `internal/uds` applies to its 0600-in-0700 invariant. `ParseUserConfig` also refuses a multi-document stream: `yaml.Unmarshal` reads document one and discards the rest, so `---` followed by `vault:` would otherwise never be looked at — precisely the failure the section check exists to prevent. `isConfigSection` is derived by reflection over `Config`'s yaml tags (`configSectionNames`, a `sync.OnceValue`) rather than hand-listed, because a hand-written list drifts *toward permissive*: a forgotten new section stops being refused and becomes merely "unknown".

**Strict at startup, lenient on reload.** `withUserOverlay` returns the loader plus a `relax` func the daemon calls once startup succeeds. A broken user file at startup is the user's immediate mistake and refusing to start names it; on a refresh tick the same error must not be fatal to everything else, because `runConfigRefresh` abandons the pass on any loader error — so a stray character in an unprivileged user's file would otherwise stop the daemon converging on remote rules and enrolments indefinitely, inverting the remote overlay's fail-open ladder for a static section that cannot apply live anyway. One-shot commands stay strict; they load once. Overruled-preference warnings fire once per field per process (`overruledWarned`), not on every 15-minute tick.

**The `enabled` ratchet is not enforceable and the docs say so.** `FUSEConfig.UserOverlayPath` (`yaml:"-"`, like `Config.Managed`) records which file contributed so `dotvault status` prints a `preferences:` line — without it an administrator seeing a mount their policy did not ask for has only a startup WARN to go on. `cache_ttl` is capped at `MaxFUSECacheTTL` (10m) in both files, since the cache window is also the window in which a revoked secret stays readable.

`ApplyUser` re-runs `validateFUSE` on the merged result (scoped: the base is already validated and the user file can only reach that section), so a bad `cache_ttl` in the user's file is a startup error naming it rather than a silent fallback to the default. Note the merged result flows into `/api/v1/config/download` and the `/ui/config/` view like any other running-config value, so an exported config carries the user's preference as though it were policy — the same property the remote overlay already has.

## Filesystem (FUSE)

`internal/vaultfs/` mounts the user's own KV subtree as a filesystem: a secret becomes a `.json` file whose contents are its data section (`jq . ~/.dotvault/gh.json`), a KV folder becomes a directory, and `stat` reports the current version's `created_time` as the file's mtime. Disabled by default (`fuse.enabled`); the daemon mounts after its first successful Vault auth and unmounts on shutdown. It is the read-anything counterpart to sync rules, which write specific fields into specific files on a schedule.

**Almost none of the package depends on FUSE.** `vaultfs.go` (the `Store` seam), `tree.go` (name resolution, the read-only guard), `document.go` (render/parse), `cache.go` and `service.go` are platform-neutral and unit-tested on every OS including Windows; only `mount_fuse.go` imports `github.com/hanwen/go-fuse/v2`, build-tagged `linux || darwin || freebsd`, and it is a pure translation layer (FUSE op in, `Tree` call out, errno back). `mount_other.go` returns `ErrUnsupported`, so `make build-all`'s `windows_amd64` target keeps building — go-fuse does not compile there, and WinFsp is a cgo DLL against dotvault's `CGO_ENABLED=0` contract. `IsMounted` (`mounted_linux.go` / `mounted_bsd.go` / `mounted_other.go`) is the statfs probe `dotvault status` uses, which asks the *kernel* rather than the daemon: the question is usually asked because the daemon looks broken.

**The user prefix is bound in the store, not the path.** `NewStore(client, kvMount, userPrefix, username)` is the only place the mount and prefix are joined, and every layer above it deals in paths relative to the mountpoint — so "a mounted filesystem cannot address another user's secrets" is structural rather than a check someone has to remember. `cleanPath` deliberately does *not* use `path.Clean`: Vault treats logical path segments literally and does not collapse `..`, so cleaning would let `a/../b` resolve to a different Vault path than the caller named. Non-canonical paths are rejected instead.

**Read-only is the default and is enforced twice.** `Tree.readWrite` gates every mutating method *and* the mount is made with the kernel `ro` option, so the guarantee does not rest on the kernel honouring a mount flag. The default holds even though the daemon's token can usually write: that capability exists for dotvault's own sync and enrolment work, and exposing it through a filesystem puts every process running as this user one stray `>` away from replacing a credential.

**Caching is a requirement, not an optimisation.** A single `ls -l` stats every entry, and stat needs a file's size, which can only be known by rendering the document — so an uncached mount turns one listing into one Vault read per secret, every time. Misses are cached too (shell completion and tools probing for config files are the bulk of a filesystem's traffic). `cache_ttl` (default 30s) bounds staleness; a write through the mount invalidates its own document and its parent listing immediately, and the kernel's entry/attr timeouts are set to the *same* value so the two layers expire together — a longer kernel timeout would serve answers the package's own cache had already dropped, with no way to reach past it.

**Write path (`fuse.read_write`).** A handle buffers the whole document (secrets are small, and a write must land as one atomic KVv2 version), and `Flush` — which the kernel calls on `close()` — parses it and writes. That ordering is what makes invalid JSON a failing `close` rather than a silently discarded edit; `dirty` is cleared only on success, so a failed close leaves the data in the handle. `parseDocument` decodes with `UseNumber` so a read-modify-write does not turn `1000000` into `1e+06`, and rejects anything that is not a JSON object with at least one field (a `touch` therefore fails, deliberately: KVv2 does not store a fieldless secret). Errors are content-free by contract — the bytes are credentials, so neither the error nor any log line derived from it may quote them.

**`Read` copies into the caller's buffer rather than returning a slice of the handle's.** Both halves matter: the kernel's read buffer is finite (128 KiB by default) and go-fuse does not clamp what `ReadResultData` is given, so returning the whole tail of a larger document overran the reply buffer and *panicked the daemon* while serialising the header — reachable on a read-write mount, since `maxDocumentSize` permits 1 MiB. Copying under the lock also removes an aliasing race, since go-fuse serialises the result after `h.mu` is released.

**The kernel does not pass `O_TRUNC` through to OPEN.** It strips it and follows with a `SETATTR` carrying a size and *no* `FATTR_FH`, so `node` tracks its open handles and a handle-less truncate is applied to all of them. Without that, `echo '{...}' > file` would leave the tail of the longer previous document behind and produce invalid JSON — `TestMountReadWriteShorterReplacementTruncates` is the regression test. `mkdir` creates an in-memory-only directory (KVv2 has no directories — a folder exists because secrets exist beneath it) that materialises when a secret is written inside it; `rename` and append are refused, the former because it would be three non-atomic Vault operations.

**`FileExtension` (`.json`) is the naming layer, and it is load-bearing twice.** It is true (the contents are JSON) and it makes editors/IDEs highlight and lint the file — the reason it exists — but it also collapses the secret-versus-folder collision a bare name creates: `users/you/databricks` and `users/you/databricks/prod` become `databricks.json` and `databricks/prod.json`, two filenames, both reachable. `Tree`'s public surface speaks *display* paths and translates to KV paths internally (`kvPathForFile` strips exactly one extension from the leaf; every earlier segment is a directory), so the FUSE layer stays free of the mapping. Exactly one extension is stripped, making it a bijection — a secret genuinely named `config.json` appears as `config.json.json`. The fold in `Readdir` is therefore done in *filename* space; what survives is the narrow case of a KV folder whose name already ends in `.json` colliding with the secret of the same stem, where the directory wins and the daemon warns once per path. `Create` refuses a name without the extension (it would rename itself on the next listing) and `Mkdir` refuses one with it (it would manufacture that collision).

**Failure is never fatal and never retried.** A host without `/dev/fuse`, without `fusermount3`, or without macFUSE still syncs, serves its API socket and runs its SSH agent. Those causes are static, so a retry loop would only log forever; the error is reported once and recorded in `Service.Status()`. A mountpoint left `ENOTCONN` by a killed daemon is detected at `prepareMountpoint` and cleared with a lazy unmount — a connected mount does not report `ENOTCONN`, so it is unambiguously ours. Shutdown retries the unmount for ~3s and then leaves it in place with a warning naming the mountpoint, rather than refusing to exit because a shell is `cd`'d inside.
